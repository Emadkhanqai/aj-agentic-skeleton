# Invariants — always on, every project, every architecture

These rules are architecture-agnostic and non-negotiable. They apply whether the project is a
monolith, microservices, or a one-file minimal API. Project-specific constraints (database
choice, container policy, cloud) live in the repo's `project-constraints.md`, generated by
`/architect` — NOT here.

## Process invariants

1. **Spec before code.** No implementation session starts without agreed acceptance criteria.
   Explore → Plan → Code → Commit; the user approves the plan, not just the diff.
2. **Never push without explicit user approval.** No `git push` to any branch or remote until
   the user says so — each time. See `standards/git-approval-policy.md`.
3. **Quality gate before every push.** Static analysis (SonarQube or configured equivalent)
   runs and reports before a push is proposed; zero Blocker/Critical/Major issues open.
4. **Classify the task and recommend the cheapest fitting model first.** See
   `model-routing.md`. If the current model outclasses the work, STOP and tell the user.
5. **Evidence or it didn't happen.** "Done" requires proof: test output, build log, or a
   verified run. Claims without evidence are treated as not done.
6. **Two-strike rule.** Same fix failed twice → stop, `/clear`, re-approach with better
   context or a smaller task. Never thrash.
7. **No new dependencies without explicit human approval** in that session. Hallucinated or
   typosquatted packages are a supply-chain attack vector.

## Code invariants

8. **Warnings are errors.** `TreatWarningsAsErrors=true`, nullable enabled, analyzers on
   (`enforcement/Directory.Build.props`).
9. **One response envelope.** Every API returns the standard `ApiResponse<T>` shape — success
   and failure alike — with a stable machine-readable `code` and a `traceId` that correlates
   with tracing. Errors flow only through the exception-handler chain, never hand-crafted in
   controllers. See `standards/api-response-format.md`, `standards/error-handling.md`.
10. **Entities never leave the API.** DTOs/records at every boundary; role-scoped projection
    for sensitive fields — enforced server-side.
11. **Validation at the edge.** Every external input is validated before it reaches domain
    logic. See `standards/input-validation-sanitization.md`.
12. **Parameterized data access only.** No string-built SQL, ever.
13. **Schema changes ship as migrations** — reviewed by a human, no destructive ops without
    explicit approval. (The migration *tool* is per-stack; the discipline is invariant.)
14. **Tests are part of the task, not after it.** New behavior lands with failing-test-first
    coverage; the suite is green before "done". See `standards/testing.md`.
15. **Secrets never appear** in code, config files, prompts, context files, or logs. Secret
    stores + managed identity only.
16. **Structured logs with correlation IDs**; no PII or secrets in logs. See
    `standards/observability-tracing.md`.
17. **Versioned public APIs.** Breaking changes create a new version; contracts never break
    silently. See `standards/api-versioning.md`.

## Security invariants

18. **Authorize server-side on every request** — never trust the client for access control.
    Guard IDOR/BOLA explicitly. OWASP Top 10 is the floor, not the ceiling.
19. **Authentication and authorization are separate concerns**; external parties get scoped,
    time-bound, revocable access — never internal SSO accounts.
20. **Audit business-critical actions** (who, what, when) in a tamper-evident way.

Everything else — layering style, project layout, mediator vs direct handlers, frontend
framework — is a playbook decision, not an invariant.
